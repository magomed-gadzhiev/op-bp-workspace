# PDM Sandbox stack (local)

Hoverfly + isolated PDM instance for testing BP changes without touching prod.

## Bring up

```
docker compose -f docker-compose.full.yml -f tools/pdm-cli/sandbox/docker-compose.sandbox.yml up -d
```

## What you get

- `hoverfly` — egress proxy. Admin API on :8888, proxy on :8500. Default mode: simulate.
- `pdm-backend-sandbox` on :8001 — copy of pdm-backend pointed at sandbox DB. HTTP/HTTPS proxied through Hoverfly.
- `pdm-postgres-sandbox`, `pdm-redis-sandbox` — fully isolated.

## Typical loop

1. Switch Hoverfly to capture (against your prod PDM, see "Capture from prod" section below):
   ```
   curl -X PUT http://localhost:8888/api/v2/hoverfly/mode -d '{"mode":"capture"}'
   ```
2. Run a BP that calls an external service.
3. `pdm fixtures record --bp <slug> --case <name> --protocol http`
4. Switch Hoverfly back to simulate (or call `pdm fixtures replay`).

## Capture from prod

For local-only Etap 2 we capture against the sandbox PDM (the only one we have).
For real prod capture see `templates/` (Task 16) — those compose files target a customer-side install.

## HTTPS

Sandbox stack uses a self-signed CA generated by `ca/generate-ca.sh`. Outputs go to
`ca/out/` (gitignored). The CA is mounted into:
- Hoverfly: as its TLS intercept cert (via `-cert`/`-key` flags)
- pdm-backend-sandbox: as a trusted root at `/usr/local/share/ca-certificates/pdm-sandbox-ca.crt`

### One-time setup

```
bash tools/pdm-cli/sandbox/ca/generate-ca.sh
docker compose -f docker-compose.full.yml -f tools/pdm-cli/sandbox/docker-compose.sandbox.yml up -d
docker compose -f docker-compose.full.yml exec pdm-backend-sandbox update-ca-certificates
docker compose -f docker-compose.full.yml restart pdm-backend-sandbox
```

The `update-ca-certificates` step is manual — backend image entrypoint isn't modified.

### Regenerate (rare)

```
rm -rf tools/pdm-cli/sandbox/ca/out
bash tools/pdm-cli/sandbox/ca/generate-ca.sh
docker compose -f docker-compose.full.yml -f tools/pdm-cli/sandbox/docker-compose.sandbox.yml restart hoverfly pdm-backend-sandbox
```

## SSH replay

`pdm-egress-ssh-replay` is up by default on host port 2222 → container 22. Drop ssh-*.yaml fixtures into `.pdm/ssh-replay-fixtures/` (this is where `pdm fixtures replay --protocol=ssh` puts them) and restart the container:

```
docker compose -f docker-compose.full.yml -f tools/pdm-cli/sandbox/docker-compose.sandbox.yml restart pdm-egress-ssh-replay
```

Test:
```
ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    -p 2222 deployer@localhost '<command>'
```
Expect a fixture-matched response or exit code 127.

## SSH bastion (capture, opt-in)

Bastion is in compose profile `bastion`. To bring it up:

```
docker compose -f docker-compose.full.yml -f tools/pdm-cli/sandbox/docker-compose.sandbox.yml --profile bastion up -d pdm-egress-ssh-bastion
```

Pre-requisites:
- Set env vars: `PDM_SSH_BASTION_TARGET_HOST`, `PDM_SSH_BASTION_TARGET_USER`
- Put an SSH private key at `tools/pdm-cli/sandbox/.ssh-bastion-keys/forward_id_rsa` (gitignored).

Captures land at `tools/pdm-cli/sandbox/captures/ssh-capture.jsonl`.

## SSH integration (Etap 3)

### Sandbox layout

- `ssh-host-keys-init` — одноразовый init-контейнер. Генерирует `host_rsa_key`+`.pub` в named-volume `ssh-host-keys` при первом старте. Идемпотентен.
- `pdm-egress-ssh-replay` — слушает порт 2222 (host) / 22 (container). Использует host-key из shared volume. Имеет network-aliases `deploy.local`, `prod.local` — любой контейнер в default-сети, обращающийся по этим именам, попадает в replay.

### Smoke-сценарий SSH replay

1. `docker compose -f docker-compose.full.yml -f tools/pdm-cli/sandbox/docker-compose.sandbox.yml up -d`
2. Положить SSH-фикстуру в `.pdm/ssh-replay-fixtures/ssh-deploy.yaml` (формат — см. design.md, секция «Формат SSH-фикстуры»).
3. `docker compose -f docker-compose.full.yml -f tools/pdm-cli/sandbox/docker-compose.sandbox.yml restart pdm-egress-ssh-replay` — replay перечитывает фикстуры при рестарте.
4. Подключиться из любого контейнера стека: `ssh -p 22 deployer@deploy.local` (или с host: порт 2222). Ожидаемо: фикстура вернёт записанный stdout.

### Per-BP bastion (prod-сценарий capture)

В prod каждому БП — свой bastion. Каждый bastion указывает на один upstream ssh-target (или несколько, если БП так устроен), но capture-файлы изолированы по BP.

Compose-стенд показывает паттерн (`--profile bastion`):
- `pdm-ssh-bastion-payroll` (host port 2223) — `BASTION_BP_SLUG=payroll`
- `pdm-ssh-bastion-deploy`  (host port 2224) — `BASTION_BP_SLUG=deploy`

Captures лежат под `tools/pdm-cli/sandbox/captures/<bp>/ssh-capture.jsonl`.

В client-project'е:

```bash
# Скопировать captures с заказчика:
rsync -av customer:/var/pdm/captures/ ./.pdm/ssh-captures/

# Записать фикстуру per-BP:
pdm fixtures record --bp payroll --case happy-path --protocol ssh
# → читает .pdm/ssh-captures/payroll/*.jsonl
# → пишет processes/payroll/fixtures/ssh-happy-path.yaml
```

Для legacy single-file сценария по-прежнему работает `PDM_SSH_CAPTURE_FILE=/path/to/file.jsonl pdm fixtures record …` или `--ssh-capture /path/to/file.jsonl`.

### Маршрутизация SSH-клиента

Sandbox — через network-aliases (`deploy.local` → `pdm-egress-ssh-replay`).

Prod — через `~/.ssh/config` `ProxyJump` на bastion:
```
Host deploy.local
    ProxyJump bp-payroll-bastion
    User deployer
```
или через DNS-override / `extra_hosts` (см. `sandbox/templates/`).
