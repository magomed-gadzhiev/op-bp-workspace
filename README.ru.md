# Воркспейс БП — Cline + `pdm ws`

Рабочее место менеджера для правки бизнес-процессов (БП) PDM с ИИ-помощником
[Cline](https://cline.bot) в VS Code. Схема работы — «код-песочница»: файлы
определения БП выгружаются в локальный каталог `workspace/<slug>/`, агент
Cline правит их по правилам [.clinerules](.clinerules), CLI `pdm ws` проверяет
и сохраняет результат на сервер **как тестовую версию**. Применение тестовой
версии (публикация) — только человек в PDM UI.

Этот репозиторий — read-only зеркало обвязки из монорепы владельца: клонируй,
обновляй через `git pull`. Права записи в зеркало ни у кого из менеджеров нет.
Каталог `workspace/` (данные определений БП) в git не попадает — мастер
определений БД PDM, не git.

## 1. Установка VS Code + Cline

1. Установи [VS Code](https://code.visualstudio.com/) (стабильная версия).
2. Установи расширение Cline: Extensions (`Ctrl+Shift+X`) → поиск **«Cline»**
   → Install (издатель — Cline; исторический id расширения
   `saoudrizwan.claude-dev`). Иконка Cline появится в боковой панели.
3. Клонируй это зеркало в каталог воркспейса и открой его в VS Code —
   Cline подхватит правила из файла `.clinerules` в корне автоматически:

   ```bash
   git clone <URL-зеркала> bp-workspace
   cd bp-workspace
   code .
   ```

## 2. Подключение модели (OpenAI Compatible)

Модель — self-hosted llama-server за nginx-прокси (`/llm/v1/`), ключи выдаёт
владелец. Настройка в Cline: иконка ⚙️ (Settings) → **API Provider**:

| Поле | Значение |
|---|---|
| API Provider | **OpenAI Compatible** |
| Base URL | `http://<хост>/llm/v1` — **обязательно с суффиксом `/v1`** (Cline сам добавляет `/chat/completions` и `/models`; без `/v1` запросы уйдут не туда) |
| API Key | ключ модели — **от владельца** (это не PDM-токен) |
| Model | **Model ID вводится вручную**, не полагайся на дропдаун |

Точное имя модели возьми из `GET /llm/v1/models`:

```bash
curl -s -H "Authorization: Bearer <LLM_API_KEY>" http://<хост>/llm/v1/models
# {"object":"list","data":[{"id":"Qwen3.6-35B-A3B-UD-IQ4_XS.gguf",...}]}
```

Секция **Model Configuration** (расширенные параметры модели):

- **Context Window** — заполни обязательно (число у владельца; должен
  совпадать с фактическим контекстом llama-server — Cline режет контекст
  по этому числу, «с запасом» указывать нельзя);
- **Max Output Tokens** — заполни обязательно; меньше контекста, но с
  запасом на рассуждения модели (thinking съедает часть ответа);
- Image Support — выключить; цены (Input/Output Price) — 0.

Секция **Features**:

- включи **Use Compact Prompt** (ключевой рецепт для локальных моделей);
- у нашей модели (Qwen3.6-35B) нативный tool-calling слабый — если в
  установленной версии Cline есть чекбокс **XML Tool Calling** (Feature
  Settings), включи его: Cline перейдёт на текстовый XML-протокол тулов.
  Побочный эффект: проза ассистента приходит в конце хода, а не по токенам —
  это нормально.

Если на машине корпоративный прокси и Cline показывает «Connection error»:
добавь хост LLM в исключения — настройки VS Code → `Http: No Proxy`
(`"http.noProxy": ["<хост>"]`), перезапусти VS Code.

Гигиена контекста: задачи держи короткими; когда контекст разросся —
**New Task** в Cline (правила из `.clinerules` применятся заново).

## 3. Персональный токен PDM (PAT)

Запросы `pdm ws` к серверу PDM авторизуются персональным токеном доступа:

1. Войди в PDM в браузере → **профиль** → страница **«Токены доступа»**
   (`/api/auth/tokens/`).
2. Создай токен: имя — например «Cline-ноутбук», скоуп — **`draft`**
   (чтение + сохранение тестовых версий + тестовые прогоны).
3. Ключ вида `pdw_…` показывается **один раз** — скопируй сразу.
   Отзыв — на той же странице (кнопка отзыва рядом с токеном).

Токен не может опубликовать/отклонить версию и править published — это
серверный инвариант: применение тестовой версии всегда делает человек
через браузер.

## 4. `.env`

```bash
cp .env.example .env
# отредактируй .env: PDM_API_BASE, PDM_API_TOKEN (pdw_…), LLM_BASE_URL,
# LLM_API_KEY, LLM_MODEL — пояснения в самом файле
```

`.env` в git не попадает (см. `.gitignore`) — там токены. С настройками
Cline из §2 сверь только значения **LLM_BASE_URL, LLM_API_KEY, LLM_MODEL**
(Cline не читает `.env`). PDM_API_BASE и PDM_API_TOKEN в Cline не вводятся —
это ключи для CLI и задач VS Code; PAT в настройках Cline/VS Code не
сохраняй.

## 5. Установка CLI (`pdm`)

Готовый установщик — `scripts/uv-bootstrap.sh` из этого зеркала: сам ставит
uv при отсутствии, берёт URL зеркала из `git remote get-url origin` и
выполняет `uv tool install`. Запусти из корня клона:

```bash
bash scripts/uv-bootstrap.sh               # первая установка
bash scripts/uv-bootstrap.sh --reinstall   # обновление после git pull
```

(Windows без Git Bash: поставь uv —
`powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`
— и выполни команду из следующего абзаца вручную.)

Вручную то же самое: нужен [uv](https://docs.astral.sh/uv/), затем

```bash
uv tool install 'pdm-cli @ git+<URL-ЗЕРКАЛА>.git#subdirectory=pdm-cli'
```

где `<URL-ЗЕРКАЛА>` — URL приватного git-репозитория-зеркала (совпадает с
`git remote get-url origin`), а `#subdirectory=pdm-cli` обязателен: пакет
лежит в подкаталоге `pdm-cli/` репозитория, не в корне. Если клон сделан по
SSH в scp-форме (`git@host:path.git`) — не переписывай её вручную в команду
установки: `uv` требует форму `ssh://git@host/path.git`, её нормализует
`scripts/uv-bootstrap.sh` — проще воспользоваться им. Доступ к приватному
зеркалу uv получает через **git credential** — на Windows это Git CredentialManager (ставится вместе с Git), на Linux/macOS — `git config --global
credential.helper store` (или менеджер ключей). Не вставляйте токен прямо в
URL: он попадёт в историю shell, ps-выхлоп и логи.

Проверка: `pdm --version` и `pdm ws --help`. Задачи VS Code
(Terminal → Run Task…) запускают `pdm ws` через `uv run --env-file .env` —
терминал не нужен ни на Linux, ни на Windows.

**Если CLI падает** (ImportError, ValidationError, неожиданный traceback) —
почти всегда устаревшая установка: `git pull` обновляет обвязку, но не
переустанавливает пакет CLI. Лечение — одной командой:

```bash
git pull && bash scripts/uv-bootstrap.sh --reinstall
pdm --version   # версию прикладывай к любому обращению по проблемам CLI
```

Агент Cline не правит код установленного пакета сам — обновление делает
человек (правило в `.clinerules`; агент обязан остановиться и попросить).

## 6. Типовой сценарий

1. `git pull` (обновить обвязку), открыть каталог в VS Code.
2. **Terminal → Run Task… → `ws-init`** → ввести слэг БП (например `lem`).
   Определение выгружается в `workspace/<slug>/`. Если у БП есть
   тестовая версия — выгрузится именно она (последнее сохранённое
   состояние), действующая версия не меняется. Чужой БП → 403: править
   можно только свои (где ты админ).
3. В панели Cline описать задачу («перенеси согласование сметы с этапа 2
   на этап 3»). Агент правит файлы по `.clinerules`: цикл
   `ws init → правка → ws check → ws test → ws report → СТОП`.
4. Задача **`ws-check`** — офлайн-валидация без похода на сервер (можно
   гонять сколько угодно).
5. Задача **`ws-test`** — сохранение в тестовую версию + тестовый прогон;
   ответ CLI содержит номер тестовой версии и diff-сводку. Идентичный
   повтор — no-op. Нет входных данных для прогона — задача
   **`ws-test-norun`** (только сохранение, без старта прогона).
6. Перед сохранением полезна самопроверка **`pdm ws diff <slug>`**
   (терминал): показывает ровно те файлы, которые изменятся относительно
   последнего сохранения.
7. Задача **`ws-report`** — diff-сводка, live_impact и чек-лист; агент
   заполняет копию шаблона в `workspace/_reports/<slug>-<дата>.md`
   (сам шаблон `templates/report-checklist.md` не правится — он придёт
   следующим `git pull`).
8. **Человек в PDM UI**: открыть БП → секция «Тестовая версия» → сверить
   diff → «Применить». После применения прежняя published-версия уходит
   в архив, тестовые прогоны отменяются автоматически.

Один БП за сессию; запускать задачи — из корня клона зеркала (там `.env`
и `workspace/`).

  чтобы проверять агента.

## 8. Как выдать права администратора БП (для владельца)

Править/сохранять БП может его **администратор**: в PDM UI открой карточку
процесса (`/pdm/management/processes/<id>`) → поле «Администраторы» →
добавь пользователя. Через REST это поле не пишется — только UI (или
`manage.py shell` на сервере). После этого пользователь выпускает себе PAT
в профиле (раздел «Токены доступа») и работает с этим БП в воркспейсе.

## 9. Границы

- Агент не публикует, не коммитит, не трогает чужие БП — правила в
  [.clinerules](.clinerules), дубль на сервере (права PAT).
- MCP-контур LibreChat и админский контур `pdm compile/push` — отдельно,
  здесь не используются.
- Вопросы по установке/ключам — к владельцу стенда (ключ модели, URL
  зеркала, значения Context Window / Max Output Tokens).
